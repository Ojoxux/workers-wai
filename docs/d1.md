# D1

`Cloudflare.Workers.D1` (`haskell/cloudflare-workers`) is a typed binding for
Cloudflare D1, the SQLite database of Workers. It sends SQL with positional
`?` parameters and returns rows as `D1Value`s.

## Configuring a binding

Declare the database in `wrangler.toml`; `binding` is the name passed to `d1`:

```toml
[[d1_databases]]
binding = "DB"
database_name = "my-database"
database_id = "<id from `wrangler d1 create`>"
```

## Usage

```haskell
import Cloudflare.Workers.D1

example :: Env -> IO ()
example env = do
  db <- d1 env "DB"
  _ <- execute db (Statement "INSERT INTO users (name) VALUES (?)" [D1Text "Ada"])
  D1Rows cols rs <- query db (Statement "SELECT id, name FROM users WHERE name = ?" [D1Text "Ada"])
  print (cols, rs)
```

| Function | Does |
|---|---|
| `d1 env name` | The binding with that name. Throws `EnvMissing` if absent and `D1Exception` if it is not a D1 database. The check looks for `prepare` and `batch` methods, so it is best effort: a service binding or Durable Object stub also passes and fails on first use. |
| `query db stmt` | Runs a statement and returns `D1Rows`: the column names and the rows, in column order. Duplicate column names are kept, and an empty result still has its column names. |
| `execute db stmt` | Runs a statement for its effect and returns a `D1RunResult`. |
| `batch db stmts` | Runs the statements as one atomic batch and returns one `D1RunResult` each. `batch db []` returns `[]` without calling D1, which rejects an empty batch. |

`D1RunResult` has `changes :: Int64` and `lastRowId :: Maybe Int64`.
`lastRowId` is the connection's `last_insert_rowid()` after the statement: the id
of the most recent successful INSERT, which a later UPDATE, DELETE or SELECT
still reports, and `Just 0` before any insert. It is `Nothing` when the id is
outside the exactly representable range (below); it is not thrown, because the
statement has already run.

## Values

Values cross the boundary as JavaScript values.

| `D1Value` | SQLite | Notes |
|---|---|---|
| `D1Null` | NULL | |
| `D1Integer Int64` | INTEGER | Exact only within ±(2^53 − 1). |
| `D1Real Double` | REAL | NaN and ±Infinity are rejected. |
| `D1Text Text` | TEXT | |
| `D1Blob ByteString` | BLOB | |

What follows from that:

- **Integer range.** Binding an integer outside ±(2^53 − 1) throws
  `D1Exception` instead of rounding. Reading a whole-number value of 2^53 or
  more throws too, and that includes a REAL column holding, say, `1e20`: a
  JavaScript number cannot tell it from an out-of-range integer. Read such a
  column with `CAST(col AS TEXT)`.
- **REAL `1.0` reads back as `D1Integer 1`.** JavaScript numbers do not
  distinguish integers from reals, so a whole-number REAL arrives as an
  integer.
- **Every number is bound as a REAL**, `D1Integer` included. A column with
  INTEGER affinity converts a whole number back to an integer, but a TEXT
  column stores `5` as `"5.0"`, and `? / 2` is real division.
- **Non-finite reals** are rejected with `D1Exception`, since D1 would store
  them as NULL.
- **Text** may contain NUL and round-trips intact, but SQLite's `length()` stops
  counting at the first NUL.
- **BLOBs** come back from D1 as arrays of numbers; the binding converts them to
  `D1Blob`.

## Batches

`batch` maps to `db.batch()`, which runs the statements in one transaction: if
any fails, none takes effect. It returns only run results (changes and row id),
not rows, because the results of a batch are consumed as effects; use `query`
for reads.

## Errors

- `D1Exception`: an error reported by D1 (syntax, constraint, wrong number of
  bindings, ...), a binding that is not D1, an integer outside the exact range,
  or a non-finite real. Its message keeps D1's own text, for example
  `D1_ERROR: near "SELEC": syntax error at offset 0: SQLITE_ERROR`, and
  `displayException` prefixes it with `d1: `.
- `EnvMissing` (from `Cloudflare.Workers.Env`): no binding with that name.

## Migrations

The schema is managed by wrangler, not by this library:

```sh
wrangler d1 migrations create DB add_users
wrangler d1 migrations apply DB --local     # or --remote
```

## Testing

D1 exists only on workerd; Node has no D1, so `test/*.test.mjs` cannot cover it.
`node scripts/check-wrangler.mjs` runs the D1 checks against `wrangler dev`.
`test/wrangler.toml` declares a local database as binding `DB` with a
placeholder `database_id`, which `wrangler dev` accepts, and the checks call the
`/d1/*` routes of `test-worker`.
